1. Executive Summary

The Galecto project has a strong product direction and a credible microservice-based observability platform shape, but it is not yet implemented to the level claimed in the documentation. The codebase already contains the core building blocks for authentication, telemetry ingestion, log search, trace visualization, replay, alerting, monitoring, project management, and retention management. However, many of these capabilities are only partially wired together, and several high-value enterprise features remain either non-functional, UI-only, or structurally incomplete.

The current state is best described as a promising product prototype or an MVP-plus platform rather than a finished enterprise-grade observability suite.

High-Level Conclusion

The platform direction is solid. The biggest immediate need is not adding flashy new UI, but closing the core correctness gaps: route prefix mismatches, auth model inconsistency, missing trace parent linkage, incomplete project APIs, hardcoded retention behavior, and non-persistent alerting.

Important: The file docs/CURRENT_IMPLEMENTATION.md currently states that all phases are complete. The codebase does not support that claim today. This mismatch should be corrected to avoid confusion for developers, reviewers, stakeholders, and potential customers.

4. What Is Implemented Well

Service Decomposition

The project is already organized into focused services for gateway, auth, query, log processing, alerting, and frontend presentation. That separation will help future scaling and team ownership.

Clear Product Direction

The feature set is cohesive. Traces, logs, metrics, replay, alerts, and project-level control all fit together into a strong observability narrative.

ClickHouse-Centered Querying

The use of ClickHouse for telemetry analytics is an appropriate choice for observability-style workloads and supports low-latency aggregation patterns.

Frontend Surface Area

The application already has a broad UI footprint, which means the product vision is tangible and not just backend scaffolding.

Concrete Strengths

  • Signup flow creates organization, default project, and initial API key at bootstrap time.
  • Kafka-based decoupling between ingestion and analytics is already present.
  • The query layer already contains logic for traces, anomalies, metrics, and logs.
  • The alert-service already has a working consumer loop for basic anomaly heuristics.
  • The frontend has dedicated workspaces for traces, logs, replay, alerts, monitoring, developer setup, and settings.

5. What Is Going Wrong in the Project

Summary: the main problem is not lack of ambition. The main problem is inconsistency between the documented architecture, the UI assumptions, the auth model, and the actual backend route and data wiring.

5.1 Route Prefix Mismatches Break End-to-End Flows

The frontend calls trace APIs using paths such as /api/v1/traces, /api/v1/traces/anomalies, and /api/v1/traces/metrics. However, the query service registers trace routes at the root level rather than under the /api/v1/traces prefix.

Evidence: apps/query-service/src/server.ts registers traceRoutes directly, and apps/query-service/src/routes/trace.routes.ts defines paths as /, /anomalies, /metrics, and /:traceId.

5.2 Auth Model Is Split Between JWT Sessions and API Key Validation

The frontend authenticates with JWTs stored in local storage, while the gateway ingest and replay endpoints expect Bearer tokens to be API keys cached in Redis. This means the UI and gateway are speaking two different auth languages.

Evidence: apps/frontend/src/lib/apiClient.ts sends the browser token as a Bearer token, while apps/api-gateway/src/middleware/auth.ts looks that same Bearer token up as apikey:{token} in Redis.

5.3 Project APIs Assume User Context That Is Not Established

Project controllers read (req as any).user.organizationId, but there is no visible middleware on those routes populating req.user through JWT verification. As a result, the project management path is structurally incomplete.

5.4 Trace Schema Cannot Fully Support Claimed Hierarchical Stitching

The trace controller builds trees using parent_span_id, but the ClickHouse events table does not store parent_span_id at all. This limits accuracy and makes some of the causality claims stronger than the actual stored data model.

5.5 Replay Depends on Narrow Metadata Assumptions

Replay logic reads a single event payload, parses method, URL, headers, and body from it, and replays through the gateway. That can work for controlled demos, but it is fragile for production use without a dedicated replay-safe request capture schema and redaction strategy.

5.6 Alerts Are Not Durable

Incidents are held in memory only. If the alert-service restarts, the alert history is lost. This makes the current incident center unsuitable for enterprise operations, auditing, or shift handoffs.

5.7 Several UI Controls Are Presentational Only

Buttons such as + New Key, Rotate Keys, Create New Rule, View Replay History, and the retention update control do not appear to be connected to complete backend capabilities.

6. Detailed Gap Analysis by Domain

6.1 Authentication and Tenant Isolation

  • JWT issuance exists, but JWT verification and role-based request authorization are not consistently enforced across services.
  • Gateway API key auth relies on Redis cache presence rather than a robust lookup and rotation strategy.
  • The platform does not yet clearly separate human user auth from machine ingest auth in a clean way.
  • There is no visible RBAC model beyond a basic Role enum.

6.2 Data Model and Persistence

  • ClickHouse event schema is too narrow for a serious tracing/replay product. It lacks explicit parent span storage, status normalization, request metadata columns, replay metadata, and lifecycle fields.
  • Alerts are not persisted.
  • Retention settings are modeled in Postgres but not operationalized in the worker logic.
  • The seed path appears inconsistent with the current Prisma schema expectations, which suggests schema and seed drift.

6.3 Observability Product Depth

  • Metrics are currently limited to simple aggregates derived from generic event payloads.
  • There is no evidence of SLOs, burn-rate alerts, service dependency maps, or release/environment correlation.
  • Replay lacks versioning, replay comparison summaries, request redaction, and outcome storage.

6.4 Frontend-to-Backend Contract Quality

  • Several pages assume APIs that are not actually exposed under matching route prefixes.
  • Some dashboard visualizations still contain static or decorative data rather than live domain-backed metrics.
  • There is no visible contract layer or shared API schema enforcement between frontend and backend.

6.5 Operational Readiness

  • No visible test coverage for critical flows.
  • No visible deployment hardening, health dependency checks, circuit breaking, or backpressure strategies.
  • No durable audit trail for admin actions, alert resolutions, key rotations, or replay usage.
  • No evidence of compliance-focused controls such as secret management, encryption policy, or data retention governance per tenant.

  • Role-based access control with organization admin, developer, observer, and billing/admin roles.
  • API key lifecycle features: create, rotate, revoke, expiry, scope, and audit history.
  • Persistent incident management with severity, assignment, notes, SLA timestamps, and change history.
  • Notification integrations for Slack, email, Teams, PagerDuty, and webhooks.
  • Saved searches, dashboards, and user-configured alert rules.
  • Release correlation and deploy markers for incident analysis.
  • OTLP and OpenTelemetry SDK support instead of only custom event ingestion.
  • Replay safeguards: PII masking, target environment controls, allowlists, and redaction policies.
  • Service map, dependency map, anomaly trends, and SLO burn-rate views.

7.3 Engineering Maturity Improvements

  • Add shared typed API contracts between frontend and services.
  • Add integration tests for signup, login, project creation, trace query, replay, and alert resolution.
  • Add schema migration discipline for ClickHouse and Postgres.
  • Add structured error taxonomies and consistent response envelopes.
  • Add internal telemetry for the Galecto platform itself.
  • Add CI pipelines with lint, typecheck, integration test, and migration validation stages.

  • Normalize event schema and add missing tracing columns.
  • Make project creation, key generation, and retention settings work end to end.

Phase 2: Make Core Data Durable and Trustworthy

9. Recommended Order of Work

The most effective way to proceed is not feature by feature in random order. This project should be handled in a dependency-aware sequence, because several visible UI issues are actually caused by deeper backend contract and schema problems. The right approach is to stabilize the foundations first, then wire core product flows, and only after that expand into enterprise capabilities.

9.1 What to Look At First

Step Area / Service Why It Comes First Main Goal
1 Project-wide contracts and route mapping Before fixing features, the team must know which frontend pages call which backend routes and whether the paths match. Create a clear map of frontend pages to actual service endpoints.
2 Authentication model across frontend, api-gateway, and auth-service Auth inconsistency is currently breaking or weakening multiple flows at once. Separate human-user JWT auth from machine API-key auth and enforce both correctly.
3 query-service route structure The traces, anomalies, and metrics pages depend on this service and currently appear misaligned. Make route prefixes and handlers match frontend expectations exactly.
4 Telemetry schema in log-service and packages/clickhouse Trace quality, replay correctness, and metrics depth all depend on what gets stored. Add missing fields such as parent span ID and normalized request/response metadata.
5 auth-service projects, API keys, retention settings These are platform-control capabilities and should work before advanced UI polish. Make project creation, key generation, and tenant settings functional end to end.
6 Core product flows: traces, logs, replay, alerts, monitoring Once contracts and storage are correct, these features can be made reliable instead of cosmetic. Turn each major workspace into a complete working user journey.
7 Enterprise features and governance These are important, but they should be built on a stable platform core. Add durability, RBAC, notificationing, auditing, compliance, and operational controls.

9.2 Recommended Sequential Approach

  1. Start with a service and route audit. Confirm which frontend pages depend on api-gateway, query-service, auth-service, and alert-service. Document the expected endpoint path, the actual registered path, the auth method used, and whether the page is currently functional.
  2. Fix authentication and authorization next. Decide the platform contract clearly: browser users should authenticate with JWT sessions, while telemetry producers should use scoped API keys. Then enforce that decision across the gateway and service routes.
  3. Repair the query-service before improving the dashboards. The traces, anomalies, and metrics pages depend on query-service behavior, so the service route prefixes and response shapes must be stabilized before doing more frontend work.
  4. Upgrade the event schema and ingestion model. Add the fields necessary for real trace hierarchies, replay-safe capture, environment/project tagging, and stronger metrics. Without this step, later observability features will remain shallow.
  5. Complete project and platform settings in auth-service. Make sure project listing, project creation, API key generation, API key caching or lookup, and retention policy updates all work in a real end-to-end flow.
  6. Then stabilize the five user-facing product pillars in order: traces first, logs second, replay third, alerts fourth, monitoring fifth. This order works well because traces and logs are the base evidence layer, replay depends on both, alerts depend on meaningful telemetry, and monitoring becomes more trustworthy once the underlying data model is solid.
  7. Only after the above should the team move into enterprise expansion work such as RBAC, incident lifecycle workflows, notifications, SDK packaging, compliance features, and advanced analytics.

  • Feature 1: Authentication and access model
  • Feature 2: Trace list and trace detail correctness
  • Feature 3: Log search stability
  • Feature 4: Replay capture and replay execution reliability
  • Feature 5: Project management, API keys, and retention settings
  • Feature 6: Persistent alerting and incident workflows

Practical advice: do not start by polishing the UI further. The first pass should focus on contracts, auth, routes, schema, and persistence. Otherwise the team risks spending time beautifying pages that are still backed by incomplete or inconsistent backend behavior.

10. Market Competition and Galecto USP

To understand where Galecto fits, it is important to compare it not only against generic monitoring tools, but against modern observability platforms that already combine logs, metrics, traces, real user monitoring, session replay, and incident workflows. As of May 10, 2026, Galecto's closest competition is not a single company but a cluster of platforms serving adjacent needs at different levels of maturity.

10.2 Where Galecto Fits in This Market

Galecto does not currently compete by breadth, maturity, or enterprise completeness. Today, the larger platforms clearly exceed it in stability, integrations, governance, alerting depth, access control, and operational trust. Galecto's most credible market position is different: it can compete as a more opinionated platform built specifically around debugging causality and verifying fixes, rather than only visualizing telemetry.

10.3 Galecto's Strongest USP

Galecto's clearest differentiator is this: not just observability, but causality replay for fix verification.

Most current observability tools help teams answer questions like:

  • What failed?
  • Where did latency increase?
  • Which service or dependency was involved?
  • What did the user experience look like?

Galecto's concept aims to go one step further:

  • Capture the request and context behind a failure.
  • Reconstruct the causality path.
  • Replay the request in a controlled manner.
  • Compare old and new outcomes to validate whether a fix actually worked.

That workflow is the most compelling strategic differentiator in the project. It turns observability from a read-only diagnosis tool into a verification-oriented debugging system.

10.5 Honest Positioning Assessment

At present, Galecto's USP is stronger as a product concept than as a production-ready implementation. That is not a weakness in vision, but it does mean positioning must be honest. The project should not currently be presented as a broader or more complete alternative to Datadog, New Relic, or Grafana Cloud. Instead, it should be positioned as a platform with a promising differentiator in replay-centered debugging and incident verification.

The most accurate near-term positioning would be:

Galecto is best framed as an observability plus production replay verification platform, not just another observability dashboard.

10.6 Strategic Recommendation

  • Do not try to beat large incumbents on total feature count in the short term.
  • Do not pitch the platform as simply a cheaper Datadog or New Relic alternative.
  • Double down on the trace-to-replay-to-verification workflow as the core identity.
  • Build credibility first by making replay technically real, safe, and auditable.
  • Then expand outward into enterprise-grade observability capabilities around that core loop.

11. Final Verdict

Galecto is not a broken idea. It is an under-finished implementation of a strong idea.

The project already demonstrates meaningful progress in system decomposition, frontend experience, Kafka-to-ClickHouse data movement, and the broad outline of an observability platform. The biggest challenge is that the current codebase has not yet crossed the line from feature-shaped prototype to production-grade enterprise system.

If the team first closes the correctness gaps, aligns the auth and route contracts, expands the data model, and persists key operational entities, the project could mature into a serious platform. Without those changes, the current documentation will continue to overstate the true implementation level.

Bottom line: the project is best represented today as a strong MVP with enterprise ambition, not as a fully complete enterprise observability suite.
